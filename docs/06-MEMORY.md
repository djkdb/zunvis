# JUNVIS — Personal Memory 설계

> 단계: **설계** (다섯 번째 Bounded Context)
> 선행: Project Brain, Creator Mode, Daily Brief, Voice
> 목표: JUNVIS가 사용자를 장기적으로 이해한다

---

## 0. 원래 계획에서 바꾼 것

1단계 분석은 이렇게 정했다.

> ② **서술적 기억**(대화, 선호, 일화)은 Mem0에 위임한다.

**기본값을 바꾼다.** Mem0를 로컬로 돌리려면 Qdrant와 임베딩 모델이 함께 떠 있어야
한다. "썸네일은 3단어 이하로" 한 줄을 기억시키려고 벡터 DB를 세우라는 것은
로컬 우선이 아니라 진입 장벽이다. 게다가 Mem0의 기본 설정은 OpenAI로 나간다 —
개인 기억이 외부로 나가는 것은 우리 원칙에 정면으로 어긋난다.

그래서:

| 층 | 구현 |
|---|---|
| 구조적 기억 (프로젝트·커밋·콘텐츠) | 자체 SQLite — 이미 있다 |
| 서술적 기억 (선호·일화·습관) | **자체 SQLite + FTS5** |

바뀌지 않은 것은 **저장소를 인터페이스 뒤에 둔다**는 결정이다. 그 덕분에 이
선택은 되돌릴 수 있다. 의미 검색 품질이 아쉬워지면 `MemoryRepository`를
구현하는 Mem0 어댑터를 하나 더 만들면 된다.

> **Mem0 어댑터는 아직 만들지 않았다.** 이 저장소에서 mem0를 설치·실행할 수
> 없어 동작을 확인할 방법이 없고, 검증되지 않은 어댑터 150줄은 쓰이기 전에
> 썩는다. 이음매(`MemoryRepository`)만 열어 두고, 실제로 필요할 때 만든다.

## 1. digest — 이 Context의 심장

1단계에서 `isair/jarvis`로부터 배운 것 중 하나가 **memory digest**였다.

> 회상 내용을 짧게 압축 후 주입 → 소형 모델의 프롬프트 길이 열화 방지

회상 결과를 그대로 프롬프트에 부으면 로컬 소형 모델이 무너진다. 그래서 회상과
주입은 다른 일이다.

```
recall(query)  →  MemoryHit[]  →  digest(budget)  →  프롬프트에 넣을 몇 줄
```

`digest()`의 규칙:
1. **고정(pinned)된 기억이 먼저.** 사용자가 "이건 항상 지켜"라고 한 것.
2. 정규화 후 중복 제거. 같은 사실이 표현만 달리 두 번 들어가지 않게.
3. 점수 순으로 예산이 허용하는 만큼. 점수 = 관련도 + 최근성 + 회상 빈도.
4. 한 줄이 너무 길면 자른다. 기억 하나가 예산을 독차지하지 않게.

## 2. 무엇을 기억하는가

브리프의 Personal Memory 항목을 두 갈래로 나눈다.

| 브리프 요구 | 어디서 오는가 |
|---|---|
| 자주 쓰는 프롬프트·모델·MCP·작업 시간 | **Trace** — 이미 `TraceHabitAnalyzer`가 한다 |
| 개발 습관·콘텐츠 제작 습관 | 이벤트 학습 (아래) |
| 선호하는 UI·규칙 | 사용자가 명시적으로 남긴 기억 |

즉 이 Context가 새로 맡는 것은 **서술적 사실**이다. 통계는 Trace가 이미 한다.

### 이벤트로부터 배운다

```
content.published  →  "「주제」 릴스를 발행했다"        (콘텐츠 제작 습관)
project.registered →  "「이름」 프로젝트를 시작했다"     (작업 이력)
```

`voice.command_received`는 **기억하지 않는다.** 말한 것을 전부 남기면 잡음이
신호를 덮는다. 사용자가 "기억해둬"라고 한 것과 실제로 일어난 사건만 남긴다.

## 3. 실제 쓰임 — 콘텐츠 생성에 주입

기억이 어딘가에 쌓이기만 하면 죽은 데이터다. 첫 소비자는 Creator Mode다.

```
junvis remember "썸네일 문구는 3단어 이하로"
junvis reel "MCP 서버 만들기"
  → 프롬프트에 그 규칙이 digest로 실려 나간다
```

`creator`는 `memory`를 임포트하지 않는다. `MemoryDigestPort`를 자기 쪽에
선언하고, 조립 루트가 채운다 — `brief`·`voice`와 같은 방식이다.

## 4. 스코프

| 스코프 | 뜻 | 예 |
|---|---|---|
| `USER` | 사람에 대한 사실. 항상 유효 | "Ollama를 기본으로 쓴다" |
| `PROJECT` | 특정 프로젝트에 한정 | "이 앱은 Supabase를 쓴다" |
| `CONTENT` | ZUN 브랜드 콘텐츠 규칙 | "썸네일은 3단어 이하" |

Mem0의 User/Session/Agent 분리에서 가져온 개념이되, 우리 도메인 언어로 바꿨다.
회상할 때 스코프로 좁히면 관련 없는 기억이 프롬프트에 섞이지 않는다.

## 5. 구현 순서

| # | 태스크 | 완료 기준 |
|---|---|---|
| P1 | domain — 엔트리·점수·digest 압축 | 순수 단위 테스트로 압축 규칙 검증 |
| P2 | application — 기억·회상·digest | Fake 저장소로 전 유스케이스 |
| P3 | infrastructure — SQLite FTS5 (+ 선택적 Mem0) | 실제 SQLite로 회상 품질 확인 |
| P4 | 배선 — 학습 구독자·MCP·CLI·Creator 주입 | 기억이 실제로 프롬프트에 실린다 |

## 6. 하지 않는 것

- **Mem0를 필수 의존성으로.** 없어도 전부 동작해야 한다.
- **모든 대화 저장.** 잡음이 신호를 덮는다.
- **기억 자동 요약(LLM).** 쓰기마다 모델을 부르면 느려지고 비싸진다.
  압축은 `digest()`가 읽기 시점에 규칙으로 한다.
- **망각.** 삭제는 사용자가 명시적으로 한다. 조용히 사라지는 기억은 신뢰를 잃는다.
