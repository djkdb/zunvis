# JUNVIS — Voice 설계

> 단계: **설계** (네 번째 Bounded Context)
> 선행: Project Brain, Creator Mode, Daily Brief, `core/model`
> 목표: "자비스, 오늘 브리핑" 한 마디로 JUNVIS가 답한다

---

## 0. 무엇이 어려운 부분인가

음성 비서에서 실제로 어려운 것은 마이크를 읽는 일이 아니다. **언제 반응할지
결정하는 일**이다. 1단계 분석에서 `isair/jarvis`로부터 배운 것이 정확히 이것이었다.

> Wake word 오탐 문제의 실전 해법(Intent Judge + 에코 필터)이 가장 값진 자산

그래서 이 Context의 무게중심은 오디오 I/O가 아니라 **판단 파이프라인**에 있다.

```
발화 텍스트
   │
   ├─ 1. 비어 있나?                        → 무시
   ├─ 2. 내가 방금 말한 것인가? (에코)      → 무시
   ├─ 3. Wake word가 있나?                 → 없으면 무시
   │     (단, 방금 응답했다면 후속 발화 창 안에서는 생략)
   ├─ 4. 진짜 명령인가? (로컬 소형 모델)    → 아니면 무시
   └─ 5. 실행 → 응답 → 말하기
```

1~3은 순수 도메인 로직이라 모델 없이 결정적으로 검증된다. 4만 LLM을 쓰며,
`ModelRole.FAST`(작은 로컬 모델)를 쓴다 — 이 판정에 큰 모델을 부르면
말 한마디마다 몇 초씩 기다리게 된다.

---

## 1. 에코 차단이 왜 필요한가

JUNVIS가 스피커로 말하면 그 소리가 마이크로 다시 들어온다. 그대로 두면
자기 말에 자기가 반응하는 무한 루프가 생긴다. `isair/jarvis`가 실제로
겪은 문제이고, 그쪽 한계에 *"정지 명령이 에코로 걸러지는 버그"*까지 적혀 있다.

우리 방식:
- 말할 때마다 그 문장을 **최근 발화 목록**에 시각과 함께 남긴다
- 들어온 발화가 그중 하나와 충분히 비슷하면(기본 0.8) 버린다
- 창은 짧게 잡는다(기본 8초). 길면 사용자가 같은 말을 따라 할 때도 막힌다

`difflib`로 유사도를 재므로 새 의존성이 없다.

---

## 2. 후속 발화 창

매번 "자비스"를 붙이는 것은 대화가 아니다. JUNVIS가 응답한 직후
**N초 동안은 wake word 없이도** 명령을 받는다(기본 12초).

이것이 켜져 있는 동안에도 4번(Intent Judge)은 그대로 돈다. 창이 열려 있다고
아무 잡담에나 반응하면 그게 더 나쁘다.

---

## 3. 명령 라우팅은 규칙 기반이다

"무엇을 실행할지"는 LLM에 맡기지 않는다. 키워드 라우팅으로 결정적으로 정한다.

| 말 | 하는 일 |
|---|---|
| 브리핑 / 브리프 / 오늘 | Daily Brief 조립 → 요약을 읽어줌 |
| 프로젝트 | 프로젝트 목록 |
| 릴스 / 캐러셀 / 콘텐츠 | Creator Mode |
| 그 외 | "아직 그건 못 합니다" |

이유: 음성은 오인식이 잦은 입력이다. 여기에 LLM 라우팅까지 얹으면 **왜 그렇게
동작했는지 설명할 수 없는 층이 두 개**가 된다. 4번의 판정은 "명령인가 아닌가"
하나로 좁게 유지하고, 무엇을 할지는 읽을 수 있는 규칙으로 둔다.

라우터는 `voice`가 아니라 조립 루트에 산다. `voice`는 다른 feature를
임포트하지 않는다(계약 10번).

## 4. 오디오 I/O — 이 저장소에서 검증되지 않는 부분

| 부품 | 구현 | 검증 |
|---|---|---|
| TTS | macOS `say` (기본 내장, 설치 불필요) | ❌ macOS 필요 |
| TTS | `NullTts` (비-macOS·테스트) | ✅ |
| STT | `whisper-cli` (whisper.cpp) | ❌ 바이너리 필요 |
| 녹음 | `sox` (무음 감지로 발화 끝 판정) | ❌ 마이크 필요 |
| 입력 | `StdinSource` — 한 줄에 발화 하나 | ✅ |

`StdinSource`가 장식이 아닌 이유: 어떤 STT를 쓰든 파이프로 연결하면 JUNVIS가
동작한다. 판단 파이프라인이 오디오 스택과 분리되어 있다는 증거이기도 하다.

```bash
junvis listen                 # 마이크 (sox + whisper-cli 필요)
junvis listen --stdin         # 텍스트 입력 — 어디서나 동작
junvis say "안녕하세요"        # TTS 확인
```

**상시 대기 마이크와 온디바이스 Wake word는 Swift 헬퍼(`junvis-mac`)의 몫이다.**
아키텍처 문서에 이미 그렇게 잡혀 있고, 그때 `AudioSourcePort` 구현만 교체하면
1~5번 파이프라인은 그대로 쓴다.

## 5. 도메인

| 타입 | 역할 |
|---|---|
| `Utterance` | 들어온 발화 한 건 (텍스트·시각·신뢰도) |
| `WakeWordConfig` | 인식할 호출어들과 후속 발화 창 |
| `ListenerState` | 최근 내가 말한 것들, 후속 발화 창 만료 시각 |
| `GateDecision` | ACT / IGNORE_EMPTY / IGNORE_ECHO / IGNORE_NO_WAKE_WORD |
| `VoiceOutcome` | 최종 결과 (실행됨 / 무시됨 + 이유) |

`ListenerState`는 불변이다. 상태 전이가 `with_spoken()` 같은 순수 함수라
"에코 창이 언제 열리고 닫히는지"를 시계 없이 검증할 수 있다.

## 6. 구현 순서

| # | 태스크 | 완료 기준 |
|---|---|---|
| V1 | voice domain — 1~3번 게이트 | 모델 없이 결정적 단위 테스트 |
| V2 | application — Intent Judge + Speak | EchoAdapter로 4번 검증 |
| V3 | infrastructure — TTS·STT·녹음·stdin | 파서·명령 조립만 테스트 |
| V4 | 라우팅 + CLI + 배선 | stdin으로 전 파이프라인 통합 테스트 |

## 7. 하지 않는 것

- **자체 Wake word 모델 학습.** 텍스트 수준 매칭으로 시작한다.
- **LLM 기반 명령 라우팅.** §3 참조.
- **음성 클로닝.** `say`로 충분하다.
- **상시 대기 데몬.** `junvis listen`은 포그라운드 프로세스다.
  상시 대기는 Swift 헬퍼가 생긴 뒤에 다룬다.
