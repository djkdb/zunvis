# JUNVIS — Voice 설계

> 단계: **설계** (네 번째 Bounded Context)
> 선행: Project Brain, Creator Mode, Daily Brief, `core/model`
> 목표: "자비스, 오늘 브리핑" 한 마디로 JUNVIS가 답한다

---

## 0. 무엇이 어려운 부분인가

음성 비서에서 실제로 어려운 것은 마이크를 읽는 일이 아니다. **언제 반응할지
결정하는 일**이다. 1단계 분석에서 `isair/jarvis`로부터 배운 것이 정확히 이것이었다.

> Wake word 오탐 문제의 실전 해법(Intent Judge + 에코 필터)이 가장 값진 자산

그래서 이 Context의 무게중심은 오디오 I/O가 아니라 **판단 파이프라인**에 있다.

```
발화 텍스트
   │
   ├─ 1. 비어 있나?                        → 무시
   ├─ 2. 내가 방금 말한 것인가? (에코)      → 무시
   ├─ 3. Wake word가 있나?                 → 없으면 무시
   │     (단, 방금 응답했다면 후속 발화 창 안에서는 생략)
   ├─ 4. 진짜 명령인가? (로컬 소형 모델)    → 아니면 무시
   └─ 5. 실행 → 응답 → 말하기
```

1~3은 순수 도메인 로직이라 모델 없이 결정적으로 검증된다. 4만 LLM을 쓰며,
`ModelRole.FAST`(작은 로컬 모델)를 쓴다 — 이 판정에 큰 모델을 부르면
말 한마디마다 몇 초씩 기다리게 된다.

---

## 1. 에코 차단이 왜 필요한가

JUNVIS가 스피커로 말하면 그 소리가 마이크로 다시 들어온다. 그대로 두면
자기 말에 자기가 반응하는 무한 루프가 생긴다. `isair/jarvis`가 실제로
겪은 문제이고, 그쪽 한계에 *"정지 명령이 에코로 걸러지는 버그"*까지 적혀 있다.

우리 방식:
- 말할 때마다 그 문장을 **최근 발화 목록**에 시각과 함께 남긴다
- 들어온 발화가 그중 하나와 충분히 비슷하면(기본 0.8) 버린다
- 창은 짧게 잡는다(기본 8초). 길면 사용자가 같은 말을 따라 할 때도 막힌다

`difflib`로 유사도를 재므로 새 의존성이 없다.

---

## 2. 후속 발화 창

매번 "자비스"를 붙이는 것은 대화가 아니다. JUNVIS가 응답한 직후
**N초 동안은 wake word 없이도** 명령을 받는다(기본 12초).

이것이 켜져 있는 동안에도 4번(Intent Judge)은 그대로 돈다. 창이 열려 있다고
아무 잡담에나 반응하면 그게 더 나쁘다.

---

## 3. 명령 라우팅은 규칙 기반이다

"무엇을 실행할지"는 LLM에 맡기지 않는다. 키워드 라우팅으로 결정적으로 정한다.

| 말 | 하는 일 |
|---|---|
| 브리핑 / 브리프 / 오늘 | Daily Brief 조립 → 요약을 읽어줌 |
| 프로젝트 | 프로젝트 목록 |
| 릴스 / 캐러셀 / 콘텐츠 | Creator Mode |
| 그 외 | **대화로 넘긴다** (§8) |

이유: 음성은 오인식이 잦은 입력이다. 여기에 LLM 라우팅까지 얹으면 **왜 그렇게
동작했는지 설명할 수 없는 층이 두 개**가 된다. 4번의 판정은 "명령인가 아닌가"
하나로 좁게 유지하고, 무엇을 할지는 읽을 수 있는 규칙으로 둔다.

이 판단은 지금도 유효하다. 나중에 대화를 붙였지만 **규칙이 이긴다** — 모델은
규칙이 아무것도 못 잡았을 때만, 그것도 말로 답하기 위해서만 부른다(§8).

라우터는 `voice`가 아니라 조립 루트에 산다. `voice`는 다른 feature를
임포트하지 않는다(계약 10번).

## 4. 오디오 I/O — 이 저장소에서 검증되지 않는 부분

| 부품 | 구현 | 검증 |
|---|---|---|
| TTS | macOS `say` (기본 내장, 설치 불필요) | ❌ macOS 필요 |
| TTS | `NullTts` (비-macOS·테스트) | ✅ |
| STT | `whisper-cli` (whisper.cpp) | ❌ 바이너리 필요 |
| 녹음 | `sox` (무음 감지로 발화 끝 판정) | ❌ 마이크 필요 |
| 입력 | `StdinSource` — 한 줄에 발화 하나 | ✅ |

`StdinSource`가 장식이 아닌 이유: 어떤 STT를 쓰든 파이프로 연결하면 JUNVIS가
동작한다. 판단 파이프라인이 오디오 스택과 분리되어 있다는 증거이기도 하다.

```bash
junvis listen                 # 마이크 (sox + whisper-cli 필요)
junvis listen --native        # 상시 대기 + 박수 두 번 (junvis-mac 필요)
junvis listen --stdin         # 텍스트 입력 — 어디서나 동작
junvis say "안녕하세요"        # TTS 확인
```

**상시 대기 마이크와 온디바이스 Wake word는 Swift 헬퍼(`junvis-mac`)의 몫이다.**
설계대로 `AudioSourcePort` 구현(`NativeHelperSource`)만 갈아 끼웠고 1~5번
파이프라인은 한 줄도 안 고쳤다 — 박수 두 번조차 새 도메인 개념이 아니라
"이름을 부른 발화"로 바꿔 넣어 기존 게이트가 처리한다([08](08-NATIVE-HELPER.md)).

## 5. 도메인

| 타입 | 역할 |
|---|---|
| `Utterance` | 들어온 발화 한 건 (텍스트·시각·신뢰도) |
| `WakeWordConfig` | 인식할 호출어들과 후속 발화 창 |
| `ListenerState` | 최근 내가 말한 것들, 후속 발화 창 만료 시각 |
| `GateDecision` | ACT / IGNORE_EMPTY / IGNORE_ECHO / IGNORE_NO_WAKE_WORD |
| `VoiceOutcome` | 최종 결과 (실행됨 / 무시됨 + 이유) |

`ListenerState`는 불변이다. 상태 전이가 `with_spoken()` 같은 순수 함수라
"에코 창이 언제 열리고 닫히는지"를 시계 없이 검증할 수 있다.

## 6. 구현 순서

| # | 태스크 | 완료 기준 |
|---|---|---|
| V1 | voice domain — 1~3번 게이트 | 모델 없이 결정적 단위 테스트 |
| V2 | application — Intent Judge + Speak | EchoAdapter로 4번 검증 |
| V3 | infrastructure — TTS·STT·녹음·stdin | 파서·명령 조립만 테스트 |
| V4 | 라우팅 + CLI + 배선 | stdin으로 전 파이프라인 통합 테스트 |

## 7. 하지 않는 것

- **자체 Wake word 모델 학습.** 텍스트 수준 매칭으로 시작한다.
- **LLM 기반 명령 라우팅.** 실행 결정은 여전히 규칙이 한다(§3·§8).
- **음성 클로닝.** `say`로 충분하다.
- **상시 대기 데몬.** `junvis listen`은 포그라운드 프로세스다.

## 8. 대화 — 규칙 밖의 말

처음 설계는 규칙에 없는 말을 "아직 그건 못 합니다"로 끝냈다. 실사용에서
그것이 벽이었다. 사람은 비서에게 명령만 하지 않는다.

### 규칙을 버린 것이 아니라 순서를 지킨다

§3의 판단 — "무엇을 실행할지 LLM에게 묻지 않는다" — 은 지금도 유효하다.
음성은 오인식이 잦아서, **실행되는 동작**이 모델 판단에 좌우되면 왜 그렇게
됐는지 설명할 수 없다.

그래서 이렇게 나눴다.

```
발화 → 게이트 1~4 → 라우터 규칙 ──찾음──▶ 결정론적 실행 (브리핑·릴스·프로젝트)
                              └─못 찾음─▶ 대화 (말로만 답한다)
```

모델이 하는 일은 **말하는 것뿐**이다. 브리핑을 실행할지 릴스를 만들지는
여전히 정하지 않는다. 이 구분이 무너지면 "왜 갑자기 이걸 실행했지?"를
설명할 수 없는 시스템이 된다.

### 근거 없는 말을 하지 않는다

프로젝트 목록·기억·브랜드 성향을 프롬프트에 싣는다. 아무것도 모르는 채로
답하면 그럴듯한 거짓말을 하고, 그것이 개인 비서에서 가장 나쁜 실패다.

문맥 한 조각을 못 가져와도 대화는 계속된다(`_safe`). 저장소가 잠겼다고
말을 못 하게 되는 쪽이 더 나쁘다.

### 말로 듣는 답

- `ModelRole.FAST` — 말이 끊기면 대화가 아니다
- 시스템 프롬프트가 "두세 문장, 마크다운 금지"를 요구하고, 그래도 모델은
  별표를 쓰므로 `_spoken()`이 한 번 더 걷어낸다. 별표가 스피커로 나가면
  "별표 별표 브리핑"이 된다.
- 최근 6왕복만 들고 간다. 길면 로컬 소형 모델이 앞을 잊고 헤맨다.

### 두뇌는 Claude Code CLI다

`claude -p` 는 대화 한 번을 비대화식으로 처리하고 stdout으로 답을 준다.
이미 깔려 있고 이미 로그인돼 있으므로 **API 키도 Ollama도 필요 없다.**
없으면 Ollama로 내려간다(`JUNVIS_BRAIN=ollama` 로 강제할 수 있다).

게이트 4(Intent Judge)는 여전히 작은 모델이 맡는다. **이것을 지키지 못해
실제로 깨졌다** — 조립 루트가 공유 모델을 그대로 판정기에 넘기는 바람에
발화마다 `claude -p` 프로세스가 떴고, 말 한마디에 90초가 걸려 대화가 통째로
타임아웃됐다. 지금은 공유 두뇌가 Claude면 판정기만 Ollama로 내린다.
Ollama가 없으면 fail-open으로 통과시킨다 — 사용자를 무시하는 것이 잘못
실행하는 것보다 나쁘다.

**도구와 MCP를 전부 끈다.** 이유가 둘이고 둘 다 겪었다.

- *안전*: 음성은 오인식이 잦다. "자비스 그거 지워줘"가 잘못 들리면 무엇이
  지워질지 알 수 없다.
- *속도*: MCP 서버가 붙어 있으면 매 호출마다 전부 기동한다. 문맥은 JUNVIS가
  직접 실어 주므로 Claude가 파일을 뒤질 이유가 없다.

고친 뒤: 대화 6.7초, 규칙에 걸리는 명령은 0.2초(모델을 아예 안 부른다).

JUNVIS 홈에서 실행한다. 사용자의 프로젝트 폴더에서 돌리면 그쪽 세션 기록과
섞인다.

### 실행인가 질문인가

`"릴스 만들어줘"`와 `"릴스 소재로 뭐가 제일 좋을까"`는 둘 다 "릴스"를 담고
있다. 키워드만 보면 후자도 릴스를 만들어 버린다 — **실제로 그랬다.**

그래서 판단을 구하는 말(`좋을까`·`어떨까`·`추천`·`왜`)이 있고 시키는
말(`줘`·`만들어`·`보여`)이 없으면 대화로 보낸다.

이 신호는 **좁게 유지한다.** 처음에 `"뭐"`·`"어디"` 같은 넓은 의문사를
넣었더니 `"프로젝트 뭐 있어"`까지 대화로 샜다. 그건 명백히 목록 요청이고,
규칙이 잡을 수 있는 것은 규칙이 잡아야 한다.

반대로 새어 나가도 괜찮은 이유가 있다. 대화는 JUNVIS가 실행할 수 있는 말을
알고 있어서 `"그건 '오늘 브리핑'이라고 하시면 바로 됩니다"`라고 길을
안내한다. 규칙과 대화가 서로를 보완한다.

### 마이크 없이도

```bash
junvis ask "요즘 뭐부터 하면 좋을까"    # 한 번 묻고 끝
junvis ask                              # 계속 대화
```

같은 라우터를 쓴다. 타이핑한 것에는 호출어도 게이트도 없다 — 손으로 친 것은
언제나 나에게 한 말이다.
